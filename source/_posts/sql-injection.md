SQL 注入是 OWASP Top 10 的常客，也是面试和靶场里的必考题。这篇笔记从 **原理**、**检测**、**防御** 三个角度整理，重点放在「为什么会出问题」和「怎么修」。

<!-- more -->

## 一、原理：数据被当成了代码

SQL 注入的本质是：**用户输入被拼接进 SQL 语句，数据库把攻击者输入的内容当成了 SQL 代码来执行**。

以登录场景为例，后端如果这样写（伪代码）：

```python
# 反面教材：字符串拼接
sql = "SELECT * FROM users WHERE username='" + user + "' AND password='" + pwd + "'"
```

当用户输入用户名为 `' OR '1'='1` 时，拼出来的语句变成：

```sql
SELECT * FROM users WHERE username='' OR '1'='1' AND password='...'
```

`'1'='1'` 恒为真，于是绕过了认证。**问题的根源不是「过滤不严」，而是「拼接」这个动作本身**。

## 二、常见类型

1. **报错注入**：利用数据库报错信息回显数据
2. **联合查询（UNION）注入**：把查询结果拼到正常结果集里
3. **布尔盲注**：根据页面「对/错」两种状态逐位推断数据
4. **时间盲注**：根据响应快慢（`SLEEP`/`WAITFOR`）推断数据
5. **堆叠注入**：一次执行多条语句（视数据库驱动支持而定）

按注入点位置分：GET、POST、Cookie、HTTP 头、二次注入（存进数据库时无害，取出使用时才触发）。

## 三、检测思路（授权测试场景）

- **输入变异**：单引号、双引号、括号、数学表达式（`1+1`）、注释符（`-- `、`/*`）观察响应变化；
- **关键字变化**：输入 `and 1=1` 与 `and 1=2` 对比页面差异；
- **看报错**：数据库报错直接回显是高危信号；
- **自动化**：SQLMap 等工具可以辅助验证，但要注意 **限速**，别把业务扫出问题。

## 四、防御：参数化查询是根本

### 1. 参数化查询 / 预编译（治本）

```python
# 正确写法：参数化
cursor.execute(
    "SELECT * FROM users WHERE username=%s AND password=%s",
    (user, pwd_hash)
)
```

参数化查询把「SQL 结构」和「数据」分开传输，**数据永远不会被当成代码执行**。MyBatis 里用 `#{}` 而不是 `${}`，Java 里用 `PreparedStatement`，都是同一个道理。

### 2. 输入校验（辅助）

- 白名单校验格式（长度、类型、字符集）
- 特殊场景（排序字段、表名）只能走白名单映射，**永远不能把用户输入直接当标识符**

### 3. 输出编码与最小权限

- 页面输出做编码，防二次注入和 XSS 连带问题；
- 数据库连接账号只给必要的权限，**禁止 `root`/`dba` 账号跑业务查询**；
- 关闭数据库详细报错回显，统一错误页。

### 4. WAF / RASP（纵深）

- WAF 可以拦截明显的攻击特征，但 **不能替代参数化查询**——绕过 WAF 的方式太多；
- 把 WAF 当最后一道防线，不是第一道。

## 五、修漏洞的检查清单

- [ ] 全局搜索拼接 SQL 的代码（字符串拼接、`format`、模板字符串、`${}`）
- [ ] ORM/框架的「原生 SQL」接口逐一确认
- [ ] 报错信息不回显数据库细节
- [ ] 数据库账号权限最小化
- [ ] 有条件上 SQL 审计 / RASP 做兜底

## 六、一句话总结

**「拼接即漏洞，参数化即防御」**。过滤和 WAF 只是缓解措施，治本永远是把数据和代码分开。
